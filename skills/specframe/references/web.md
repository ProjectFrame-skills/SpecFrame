# Web requirements considerations

Apply only to the project's actual web workflows. Preserve existing policies and user decisions. Convert relevant unknowns into adaptive questions or explicit proposals; do not impose all capabilities. The web interaction and motion considerations below are incorporated into the operating contract.

- Work context: affected-region updates; shared shell; retained filters/search/selection/input/scroll/focus; related counts/details/aggregates; changed sort/filter membership; empty and last-page results. Choose panel, form, detail page or full navigation for the actual task; do not put everything in a modal.
- Persistence: actual server or local/mock/memory storage and refresh/device retention; distinguish confirmed save, optimistic display with rollback, upload transfer and server completion. Keep server authorization/business rules authoritative when a server exists. Never report demo storage as server persistence.
- Request states: waiting, processing, success, failure, uncertain outcome. Preserve valid input/work location; distinguish validation/network/offline/session/permission failures. Prevent repeated UI submissions without treating disabled buttons as cross-tab/server deduplication. Consider idempotency/version/conflict rules only when needed. An unknown write outcome requires reconciliation, not blind retransmission; reconciliation must not hide the result behind the old filter and must itself be retryable.
- Navigation: shareable screen/filter/selection URLs; exclude sensitive or temporary inputs from URLs; meaningful back/forward history; direct-entry versus list-entry closing; refresh/new tabs/downloads/native links; canceled navigation consistent with address; unsaved-input confirmation; focus/scroll restoration; revalidate removed/restricted data rather than trusting old caches.
- Ordering and teardown: newest user selection wins despite reversed responses; rapid re-entry/cancel/reopen; delayed/failed media; long content/small screens; cleanup requests/listeners/timers/subscriptions; no stale click targets or remaining scroll locks.
- Interaction: applicable default/hover/keyboard-focus/pressed/selected/disabled/loading states, input correction/validation/submission. Convey actionable feedback without relying only on color. Define action, response, end state, cancel/return behavior in text.
- Motion: purposeful entry/exit/cancel/re-entry, tab/panel relationships, expanding content and layout, scroll start/progress/end/reverse behavior, stable loading transition, immediate feedback without decorative delays. Prefer stable elements when motion serves no purpose. Common duration/easing/distance/scale are later implementation choices, not invented user requirements.
- Access and design: mobile layout/density/controls without hover dependence; keyboard order, visible focus and return; modal name/focus boundaries/close; reduced motion with equal functionality; status feedback not covering controls; helpful empty/failure states; consistent visual weight/icons/type/spacing/layers. Check new asset/license/loading/fallback needs if relevant; do not invent numeric speed/accessibility targets.
- Existing-project compatibility: preserve data/authentication/authorization/input/audit policies and output encoding; old/new asset and deployment compatibility; unsaved inputs/in-flight writes during version transition; refreshing persisted data; existing direct-link/SEO/non-JavaScript support where applicable. Do not assume a framework/API rewrite.
- Scope: app-like interaction does not automatically mean PWA installation, offline operation, push notifications, or real-time collaboration. Ask only when these change the user's goal or important uncertainty.
- Acceptance: connect applicable normal/empty/boundary/retry/concurrency/failure/recovery/permission/navigation/mobile/keyboard/reduced-motion/cache-version behavior to requirements. Design the tests here; actual product implementation and execution belong downstream. A screenshot, build, or URL event alone does not prove persistence, authorization, document reload, or completed interactions.
