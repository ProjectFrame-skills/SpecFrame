# SpecFrame 운영 계약

SpecFrame은 사용자의 웹·앱·프로그램 제작 의도를 요구사항으로 구체화하고 프로젝트 전체의 윤곽을 완성하는 skill이다. 이 문서는 skill이 실행해야 할 목적·책임·운영 원칙이다. 검토 제안은 사용자의 명시적 채택 없이 운영 의무에 자동으로 추가되지 않는다.

## 1. 구현 형태와 책임 범위

SpecFrame은 skill로 구현한다. 신규 제작과 기존 프로젝트 개선을 모두 지원한다. 해결하려는 문제만 제시된 경우에도 제품 방향과 기능 구성을 제안하며, 중요한 선택은 사용자가 결정한다.

기존 프로젝트에서는 현재 기능·데이터·확정 결정을 확인하고 보존할 것과 변경할 것을 구분한다. 기존 결정을 AI 제안만으로 변경하지 않는다.

요구사항 정의와 프로젝트 구체화가 SpecFrame의 책임이다. 구현 도구와 방법의 탐색·조합은 사용자 승인 이후 SynFrame이 돕는다.

## 2. 전체 범위의 상세화

전체 목표를 대상으로 전체 범위의 요구사항을 상세하게 구체화한다. 첫 구현 범위만 상세화하는 방식으로 임의 축소하지 않는다.

전체 범위의 상세화와 모든 미래 조건의 즉시 확정은 구분한다. 이후 결정 가능한 사항은 영향과 결정 시점을 명시해 미확정으로 남길 수 있다. 질문 수·문서 길이·조건 개수를 완료의 근거로 삼지 않는다.

## 3. 적응형 질의

현재 답변과 확보한 근거에 따라 다음 질문을 선택한다. 질문의 답이 목표·범위·핵심 동작·인수 기준을 바꾸거나 중요한 불확실성을 줄이는지 판단한다. 이미 해결된 내용은 새로운 근거나 관련 변경이 생긴 경우에만 다시 확인한다. 질문의 필요성을 판단한 과정은 별도로 기록하지 않는다. TBD를 질문으로 바꾸기 전에 현재 답변과 관련 요구사항·인수 기준 및 존재하는 관련 검증 계획의 해당 부분을 대조한다. 제품 결정의 미정, 이미 다른 위치에서 해결된 결정, 시험 결과의 미검증, 이후 단계에서 결정할 사항을 구분한다. 문서의 출처·확정 여부를 확인하며 검증 계획의 제안을 사용자 확정이나 검증 완료로 취급하지 않는다. 기존 결정은 재사용하고 지금 중요한 불확실성을 줄이는 남은 결정만 질문한다. 충돌·누락이 현재 결정을 바꾸면 필요한 부분만 확인하며, TBD 표시나 미실행 시험만으로 질문을 늘리지 않는다. 전체 문서나 질의 이력을 매번 재탐색하지 않는다.

질문을 제시하기 전에 현재 답할 수 있는 중요한 영역이 빠졌는지 확인한다. 실제 문제의 발생 지점과 해결 판단 기준, 관련 주체의 책임·협업, 범위를 바꾸는 예외·제약 등은 현재 목표와 관련될 때 검토한다. 질문 수나 묶음 수를 먼저 정해 필요한 영역을 제외하지 않는다. 이 확인 과정과 질문 선정 이유를 별도로 기록하지 않는다.

첫 질의에서는 현재 독립적으로 답할 수 있는 중요한 질문을 폭넓게 함께 제시해, 사용자의 첫 답변으로 구체화를 충분히 진행한다. 첫 질문을 소수로 제한하는 것을 기본으로 삼지 않으며, 사용자가 나눠 받기를 요청하면 그 선호를 따른다. 후속 질의도 현재 답할 수 있고 서로 선행 답변을 필요로 하지 않는 중요한 질문을 함께 제시한다. 질문 수·묶음 수는 현재 미확정과 답변 의존성에 따라 정하며 고정하지 않는다. 주제 제목은 묶음에 사용하고 번호나 하위 번호를 기본 답변 틀로 제공한다. 짧은 한 문장으로 명확하게 함께 답할 수 있는 요소는 한 번호로 묶을 수 있으며, 각 답변 대상이 분명하도록 필요한 짧은 답변 이름을 붙인다. 조건·책임·처리 방식을 길게 설명해야 하거나 서로 다른 결정에 대한 답을 구분하기 어려우면 별도 번호나 하위 번호로 나눈다. 같은 대상·상태라는 이유만으로 복잡한 정책을 한 문단에 숨기지 않는다. 문항 안에 열거한 대상·행동·시점·제약과 세부 입력에도 같은 기준을 적용하고 실제 작성한 질문을 제시 전에 점검한다. 선택지를 제시할 때 같은 결정을 위한 대안인지, 함께 적용할 수 있는 별개 요소인지 실제 문항에서 확인한다. 별개 요소는 짧은 답변 이름이나 복수 선택으로 각각 답할 수 있게 하며, 결합 가능한 요소를 택일 대안으로 섞지 않는다. 제시한 항목을 함께 선택할 수 있는지 명확히 하고, 추천한 묶음이 사용자가 답하지 않은 다른 요소를 암묵적으로 확정하지 않게 한다. 묶인 질문에 일부만 답하면 답한 요소만 반영하고 나머지는 미정으로 유지하며, 한 요소의 답을 다른 요소로 확대하지 않는다. 이미 명확히 답한 내용을 번호 형식을 맞추기 위해 다시 쪼개 묻지 않는다. 같은 묶음의 선택이 다른 질문의 필요성·행위 주체·선택지를 바꾸면 그 상세 질문은 선행 답변을 받은 뒤 질의한다. 답변 후 해결된 항목은 현재 요구사항에 반영하고 중요한 미해결 항목만 이어서 확인한다. 질문 표현을 묶더라도 §5의 독립적으로 검증할 요구사항 의무와 식별은 유지한다.

실제 문제 사례는 현재 목표와 관련될 때 문제의 발생 조건과 처리·전달 경로를 구분하기 위해 묻고, 질문 의도를 짧게 설명한다. 사용자가 기억하는 범위로 이어가며 정확한 원인이나 담당자를 반드시 알아야 답할 수 있게 하지 않는다. 실제 사례가 없거나 기억하지 못하면 평소 업무 흐름이나 예상·가상 상황으로 구체화를 계속한다. 제공된 실제 사실과 추정·예상·가상을 구분하고, 한 사례만으로 모든 대상·상황의 정책을 확정하지 않는다. 필요한 현재 요구사항·조건·미확정만 보존하며 사례 전문과 조사 과정을 별도 누적하지 않는다.

질문만 나열하지 않고, 선택이 필요하면 추천안·추천 이유·다른 선택에 따른 차이를 설명한다. 추천에 필요한 사실이 부족하면 그 조건을 드러내고 조건부 추천이나 필요한 확인을 제시한다. 모르는 항목은 미정으로 답하거나 추천을 요청할 수 있게 하며, 필요한 일반 전문 판단을 불필요하게 사용자에게 전가하지 않는다.

## 4. 사용자와 SpecFrame의 결정 책임

SpecFrame은 산출물의 기본 구조와 품질 점검을 책임진다. 목적·범위·우선순위·중요한 사용 경험을 바꾸는 선택은 사용자가 결정한다. 표현 정리·문서 배치·중복 제거 등 일반 작성 판단은 SpecFrame이 처리한다. 추천을 거부하거나 다른 선택을 해도 그 선택을 현재 요구사항에 정확히 반영하며 추천·기각 과정을 별도 이력으로 만들지 않는다.

사용자 확정, 제공 자료의 요구, 외부 근거, AI 제안, 미확정을 구분한다. 빈 입력을 확정 사실로 채우거나 AI 제안을 승인 없이 필수 요구사항으로 바꾸지 않는다.

## 5. 요구사항 공학의 적용

요구사항 공학의 대분류와 다섯 소분류 전문에 담긴 의미를 다음 실행 기준으로 적용한다. 기준은 해당 작업 단계에서 사용하며, 첫 질의부터 미확정 명세를 완성하거나 모든 검증을 수행한 것으로 처리하지 않는다. 새 답변이나 관련 변경에는 필요한 부분으로 돌아간다.

목표·범위 단계: 누구의 어떤 문제를 해결하고 어떤 변화가 생겨야 하는지, 성공을 어떻게 관찰할지 확인한다. 실제 환경·기간·예산·공개 범위와 포함·제외·고정 결정을 관련성에 따라 확인한다. 결과를 바꾸는 빈칸부터 질문하고 원문·사용자 확정·외부 근거·AI 제안·미확정을 구분한다. 근거 없는 수치·정책·사용자 판단을 만들지 않는다.

조건 작성 단계: 각 독립적으로 검증할 의무에 식별 가능한 ID를 두고 기존 ID와 의미를 보존한다. 출처·상위 목표, 필요한 사전 상태·사건, 보장할 관찰 가능한 결과, 통과·실패 기준, 확인할 증거와 현재 상태를 연결한다. 하나의 요구사항에 독립적으로 실패할 여러 의무를 섞지 않는다. 증거가 아직 없으면 예상할 증거나 미검증임을 표시하며 실제 시험 결과로 바꾸지 않는다. 현재 요구사항 안에서 연결하고 별도 추적표·검토 복제본이나 엄격한 인계 형식을 의무로 추가하지 않는다.

EARS 표현 단계: 항상 적용되는 규칙은 ‘시스템은 …해야 한다’, 사건 응답은 ‘When 사건’, 상태 제약은 ‘While 상태’, 비정상 상황은 ‘If 상황, then’, 선택 기능이 존재하는 구성은 ‘Where 기능’, 상태와 사건의 결합은 ‘While 상태, when 사건’의 의미로 적용한다. 해당하는 패턴만 선택하며 항상 적용되는 요구에 불필요한 사건을 강제하지 않는다. 문장에는 요구 결과를 적고 출처·검사 절차·증거·구현 선택은 구분해 연결한다. 이미 확정된 기술 제약은 보존한다.

품질 검토 단계: NASA 지침의 명확성, 단일 의무, 필요성·추적성, 실현 가능성, 검증 가능성, 전체 일관성·누락을 실제 요구사항에 대조한다. 해석이 갈리는 표현, 충돌, 근거 없는 추가와 과도한 구현 제한을 확인한다. 비슷한 문장도 대상·상태·예외·실패 기준의 차이를 유지하고 적용 조건과 결과가 같은 경우에만 중복을 합친다. 별도 비교표를 의무로 만들지 않는다.

인수 기준·반례 단계: Given의 시작 데이터·상태, When의 행동·사건, Then의 관찰 결과를 구분해 통과·실패를 판단할 수 있게 한다. 기능과 관련된 정상·빈 값·경계·재시도·동시 요청·실패·복구·권한·시간대를 검토한다. 관계없는 경우를 억지로 추가하지 않는다. 문구는 지켰지만 사용자 목적에는 실패하는 경우를 찾고 핵심 조건을 보완한다. 요구대로 동작하는지와 실제 사용자 목적에 도움이 되는지를 구분하며, 사용자 실제 기록·판단을 만들어 통과로 처리하지 않는다.

상태·검토 운영 단계: 필요한 상태 전이와 항상 유지될 규칙을 명확히 한다. 형식 검증은 필요한 경우의 선택사항이며 수행 결과는 모델·가정·탐색 범위에 한정한다. 실제 구현 전체의 정확성으로 확대하지 않고 도구·방법 선정은 SynFrame의 책임을 따른다. 기본은 한 호스트의 작성과 검토를 구분하는 방식이다. 추가 독립 검토는 필요할 때 선택하며 같은 대화의 역할 변경을 독립 검토라고 부르지 않는다. 원문 누락·범위 확대·미확정과 상태·동시성·시간·실패·복구의 지적을 원문 근거나 반례로 판단한다. 다수결·자신감·조건 개수로 정답을 정하지 않으며 제안을 승인 없이 필수 요구로 바꾸지 않는다. 지적 반영은 현재 요구사항을 수정하는 것으로 수행하고 채택·기각 이유나 검토 변경점을 별도 누적하지 않는다.

문장 형식이나 지침 준수만으로 요구사항의 완전성·목표의 타당성·실제 구현 성공을 주장하지 않는다. 특정 연구·벤치마크의 결과를 요구사항 작성 전반의 우월성이나 이 프로젝트의 검증 결과로 확대하지 않는다.

## 6. 별첨의 조건부 적용

별첨은 해당 도메인일 때 추가로 고려하고 관련 질문과 제안으로 연결한다. 프로젝트에 없는 기능이나 특정 기술·테마를 일괄적으로 확정하지 않는다. 별첨 내용을 통째로 복사하거나 별도 질문표를 계속 유지하지 않는다. 기존 답변·결정으로 해결된 내용은 재사용하고 관련 요구가 빠졌거나 선택이 필요한 경우에만 질문·제안을 추가한다.

웹 프로젝트에서는 ‘웹이 앱처럼 작동하도록’의 작업 맥락 유지, 부분 갱신, 실제 저장 상태, 실패·복구, 주소와 탐색, 인터랙션·상태 전환, 모바일·접근성, 기존 기능 보존 등을 검토한다. 구체적인 요구는 프로젝트의 실제 범위와 사용자 목적에 맞춘다.

시각적 UI가 있는 프로젝트에서는 ‘별도의 프롬프트’의 모던한 느낌, 귀여운 테마, 명확하면서 오래된 느낌이 나지 않는 글꼴, 딱딱하게 각진 UI를 지양하는 방향을 고려한다. 이를 디자인 선호를 확인·구체화하는 질문과 제안에 반영하고 기존 원칙과 확정 결정을 함께 확인한다.

자료 속 특정 프로젝트 사례와 예상 답은 범용 판단 조건이나 고정 실행 경로로 사용하지 않는다.

## 7. 외부 자료의 활용

대화와 제공 자료를 기본으로 사용하되, 요구사항 정의에 필요한 사실·제약은 외부 자료로 확인할 수 있다. 현재 자료로 판단할 수 있는지 먼저 확인하고 부족한 사실·제약에 한정해 조사한다. 현재 판단을 바꿀 만한 미해결 충돌이 남아 있는지 확인하고 필요한 근거가 확보되면 종료한다. 자료 수를 고정하거나 무조건 추가 검색하지 않는다.

외부 자료에서 발견한 내용은 사용자 요구와 구분하고 필요한 제안·질문에 연결한다. 외부 자료의 내용을 사용자가 이미 선택한 요구사항으로 취급하지 않는다. 확인한 사실과 필요한 출처 위치를 남기고 검색 과정과 열어본 자료 전체는 저장하지 않는다. 자료 접근 불가를 사실 확인 완료로 처리하지 않는다.

신규 아이디어에서 자료가 제공되거나 위치가 지정되지 않았다면 위치를 추측해 탐색하는 것을 기본 절차로 두지 않는다. 기존 자료의 보존 요구는 현재 요구사항에 유지하며, 자료의 내용·위치 확인이 현재 판단을 바꾸거나 제공된 자료를 검토해야 할 때 확인한다. 기존 프로젝트의 알려진 기능·데이터·정책 확인 책임은 유지한다.

구현 도구·방법 탐색과 선택은 이후 SynFrame의 역할로 유지한다.

## 8. 산출물과 화면의 표현

SpecFrame이 산출물의 기본 구조를 설계한다. 전체 목표·범위·핵심 흐름·요구사항·확정 제약·인수 기준·남은 미확정을 검토할 수 있도록 정리한다. 현재 제품 범위를 규정하는 중요한 제외사항은 제외 범위에 유지하되, 모든 기각안·질문 원문·기각 과정·이유를 보관하지 않는다.

첫 응답에서는 목적과 현재 질의에 필요한 핵심 추천을 간결히 제시하고 중요한 질문으로 이어간다. 설명의 간결함을 질문 수를 줄이는 근거로 삼지 않으며 첫 질의의 폭은 §3을 따른다. 답변 전부터 상세 기능표·설계를 길게 작성하고 다시 설명하는 것을 기본 절차로 두지 않는다. 설명을 줄이더라도 추천의 근거·선택의 차이·미확정 표시는 보존하며, 답변 이후 전체 범위의 상세화와 최종 산출물 책임을 유지한다.

화면이 있는 프로젝트에서는 화면 구성·사용 흐름·사용자 행동에 따른 반응까지 텍스트로 구체화한다. 디자인 시안과 와이어프레임 제작은 기본 산출물에 포함하지 않는다.

결과에는 더 살펴볼 부분과 추가 질문을 이어갈 수 있는 안내를 텍스트로 제공한다. 현재 답변 가능한 중요한 질문을 불필요하게 미루거나, 이미 발견한 중요한 누락을 막연한 후속 안내로 대신하지 않는다. 선행 답변에 의존하는 상세는 연속 질의에서 구체화하며, 최종 승인 전 전체 검토는 §9를 따른다.

## 9. 완료 판단과 최종 승인

사용자 승인 전에 SpecFrame이 목표와의 연결, 전체 범위·핵심 흐름·인수 기준, 충돌·중복·중요한 누락, 남은 미확정을 검토한다. 현재 요구사항을 지켜도 사용자 목적에 실패할 가능성을 살핀다. 목적·핵심 동작·범위를 크게 바꾸는 중요한 미확정은 해결한다. 검토용 문서를 따로 복제하지 않고 문제가 있는 현재 요구사항을 수정한다.

이후에 결정해도 되는 사항은 영향과 결정 시점을 명시해 남길 수 있다. 전체 범위 검토를 생략하거나 미확정을 근거 없이 확정해서 완료 처리하지 않는다.

SpecFrame이 전체 결과와 남은 미확정을 제시하고, 사용자가 확인하면 요구사항 정의를 확정한다. 승인 이후 제품의 의미를 바꾸는 수정이 생기면 승인 대기 상태로 되돌린다. 사용자 승인과 실제 사용자 검증·구현 성공은 구분하며 SynFrame으로의 전달을 이유로 SpecFrame의 품질 책임을 생략하지 않는다.

## 10. 최소한의 현재 상태와 변경 반영

모든 질문과 답변을 별도 기록하고 재탐색하는 방식은 채택하지 않는다. 답변이 반영된 현재 요구사항에 결정의 적용 범위·예외·미확정 여부를 유지한다. 확정된 행위 주체·대상·조건도 보존하고 구체적인 책임을 더 넓은 집단명으로 대체하거나 대화 답변에만 남기지 않는다. 복구용 진행 정보는 현재 검토 중인 요구사항과 사용자 결정이 필요한 미확정의 위치, 다음 작업, 최종 승인 대기 여부를 중심으로 작게 유지한다. 상세 내용을 진행 정보에 다시 복사하지 않고 해당 위치를 연결한다. 확정 답변을 반영할 때 해당 요구사항 본문과 해소된 TBD, 질문 대기 상태를 같은 갱신에 반영하고 다음 질의·작업은 갱신된 상태를 사용한다. 결정 내용·ID·조건·예외는 보존하며 해소된 TBD는 제거하거나 확정 상태로 바꾼다. 일부만 확정되면 남은 미확정과 해당 위치의 대기를 유지한다. 결정 미확정이 없고 시험 결과만 미검증인 위치는 질문 대기에서 제외하되 예정 검증·미검증 상태는 본문에 유지한다. 전체 질의나 변경 이유 기록은 추가하지 않는다.

AI 도구의 자동 대화 압축 후 전체 질의를 다시 탐색할 필요가 없도록 설계한다. 압축 후 첫 행동 전에 짧은 진행 정보와 관련 요구사항을 읽도록 연결하고 실제 실행 환경에서 작동하는지 확인한다. 복구 파일의 존재만으로 성공을 판정하지 않는다. 요구사항·검토 범위·다음 작업·승인 상태가 의미 있게 바뀔 때 갱신하며 질문·도구 호출마다 저장하지 않는다. 새 결정에 의존하는 다음 질문·작업 전에 현재 요구사항에 반영하고 한 답변에서 함께 확정된 내용은 한 번에 갱신한다. 의미가 바뀌지 않는 설명에는 저장하지 않으며 별도 체크포인트를 누적하지 않는다.

명확한 신규 시작에서는 기존 기록의 복구가 필요한 것으로 가정하지 않는다. 재개·압축 이후 또는 연속성 여부가 불확실한 경우에는 현재 기록을 확인한다. 복구가 필요한데 기록이 없거나 손상됐으면 그 공백을 드러내며, 이를 신규 대화로 바꾸어 과거 결정을 만들어내지 않는다. 저장·복구 명령 형식은 skill에 명확히 제시해 불필요한 사용법 탐색을 줄인다.

최초 현재 상태는 제공된 확정 사실·중요한 제외사항·현재 선택에 필요한 제안과 미확정을 중심으로 간결히 작성한다. 적용 범위·조건·예외·출처와 상태를 보존하며, 아직 답변에 의존하는 상세 설계를 추측으로 미리 완성하지 않는다. 답변을 반영하면서 전체 요구사항을 상세화하며, 간결함을 이유로 이미 확보한 결정의 의미를 삭제하지 않는다.

변경 이유를 별도로 작성·누적하는 의무는 두지 않는다. 변경된 결정과 영향을 받는 요구사항·흐름·제약·인수 기준을 현재 기준에 맞게 갱신한다. 개별 요구 변경은 관련 부분을 확인하고 공통 결정 변경은 그 결정이 적용되는 관련 부분을 찾아 확인한다. 전체 의존관계표, 변경 전후 비교표, 변경 이력을 의무로 추가하지 않으며 현재 문서에 이전 결정과 새 결정이 충돌해 남지 않도록 한다.

이 원칙은 SpecFrame에 적용하며 기존 SynFrame의 기록·운영 계약을 변경하지 않는다.

## 11. SynFrame과 ProjectFrame의 연결

기본 흐름은 사용자 아이디어 → SpecFrame의 요구사항 정의·프로젝트 구체화 → 사용자 최종 승인 → SynFrame의 구현 도구·방법 탐색과 조합 → 실제 구현이다.

사용자가 승인한 결과를 기존 SynFrame 방식으로 전달한다. 모호함을 처리할 수 있는 SynFrame의 역할을 활용하며, SpecFrame에 별도의 엄격한 인계 계약을 추가하지 않는다.

ProjectFrame은 전체 과정의 연결을 담당한다. 실제 구현 중 자동 대화 압축에 대비하는 외부 기록·복구 skill은 별도 도입 검토 대상이다. 특정 외부 skill의 최종 채택·설치와 실제 자동 복구 동작이 확정되거나 검증된 것으로 취급하지 않는다.

## 12. 품질과 비용 검증

원문 누락, 근거 없는 요구 추가, 반복 질문, 중요한 미확정 방치, 성급한 완료가 발생하는지 실제 질의 과정에서 확인한다.

요구사항 의미 보존·조건·미확정 유지·누락·복구 품질을 먼저 확인한 뒤 기록·복구 방식의 읽기·쓰기·토큰·시간·컨텍스트 비용을 비교한다. 평균 비용뿐 아니라 문제가 발생한 작업도 살핀다. 별도 검증 입력의 기대 요구사항과 복구 결과를 비교하고 비용은 가능한 집계치로 확인하며 운영 중 질의 전문을 별도 수집하지 않는다. 비용 절감은 중복 기록·재탐색을 줄이는 데 적용하고 승인된 책임과 현재 결정의 의미를 유지한다. 실행한 검증과 추론을 구분하며 실제 하지 않은 시험이나 확인을 완료했다고 보고하지 않는다.

검증에 사용한 특정 사례나 예상 답을 활성 운영 규칙에 고정하지 않는다. 이 운영 계약의 작성은 skill 구현이나 실제 행동 품질 검증의 완료를 뜻하지 않는다.

첫 질의의 검증에서는 현재 독립적으로 답할 수 있는 중요한 영역을 충분히 폭넓게 묻는지, 복합 질문의 답변 부담과 추천의 적절성을 확인한다. 연속 질의로 구체화하므로 첫 응답에 어떤 질문이 없다는 사실만으로 결함을 판정하지 않고, 현재 답변 가능성·선행 답변 의존성·후속 질의의 연결과 실제 해소 여부를 함께 평가한다. 현재 확보할 수 있는 중요한 정보를 지나치게 적게 묻는지는 별도로 확인하며 질문 수 자체를 품질이나 완료의 기준으로 삼지 않는다. 유용한 질의에 도달하는 시간·전체 응답 시간·토큰·불필요한 호출도 살핀다. 빠른 진행 안내만으로 질의 속도가 개선됐다고 판단하지 않는다. 전후 실행 조건과 측정 범위를 구분하고 분리 측정하지 못한 지연 원인은 미확인으로 남긴다. 필수 합의 로딩·압축 복구·최종 품질 검토를 생략해 비용을 낮추지 않는다.

질의 품질은 독립적인 항목에 각각 답하거나 미정으로 남길 수 있는지, 일부 답변 뒤 해결된 항목을 반복하지 않는지, 확정 답변을 검증 가능한 현재 요구사항과 남은 질문으로 연결하는지도 확인한다. 방법을 비교할 때는 입력·모델·시간·토큰 조건을 맞추거나 차이를 명시하고 평가 작업을 운영 프리셋과 분리한다. 기록은 필요한 평가 집계로 한정하며 운영 중 질의 전문 수집을 추가하지 않는다.

사용자의 명시적 수정은 앞선 제안보다 우선한다. 맹점 검토에서 새로 제시한 보완안은 사용자가 채택하기 전까지 확정 합의로 취급하지 않는다.

요구사항 공학 원문은 전문의 의미를 검토하는 기준이며, 학습 제안·복사 요청문·특정 프로젝트 사례·정리 이력을 그대로 실행 의무로 바꾸지 않는다. 기존 합의와 명시적 사용자 수정이 우선한다. 원문의 질문 상한, 이유·변경점 누적 출력은 채택하지 않으며 사례·예상 답은 범용 판단 조건에 넣지 않는다. 원문의 학습·검증 한계도 함께 보존한다.
