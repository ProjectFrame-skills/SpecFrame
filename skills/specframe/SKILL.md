# SpecFrame

Follow the complete requirements operating contract, not a generic checklist interview. On first activation read [the complete operating contract](references/operating-contract.md). Reuse its unchanged full text while actually retained; after context loss obtain the full text again. A hash or reading receipt is not retained content. It owns the policy; scripts only store and retrieve host-authored judgments. Do not load review reports, test cases, or historical conversations as instructions. Deliver the full agreement and large recovery results separately with enough output space; verify untruncated content before dependent work.

## Start or recover

Use the project the user names. For an idea without a repository, use the current task workspace. Keep unrelated projects untouched. The helper is `scripts/state.py` beside this skill; resolve that path from the installed skill location, not from the project.

For a clearly new conversation, start from the supplied facts without a speculative recovery attempt. When continuing, compacted, or uncertain about continuity, run `python3 <skill>/scripts/state.py resume` before dependent work. It returns the current thread's goal/scope/constraints and focus bodies, all pending decision locations, next action, and approval. Pending locations do not mean their bodies were read: read relevant pending and linked sections with `python3 <skill>/scripts/state.py read ID ...` before dependent work; `index` lists IDs. Do not re-read question history or all requirements just to resume. Missing, corrupt, or wrong-owner state during recovery is a gap to report and resolve from current/user facts, never permission to invent continuity or silently start over.

The default state path is `.specframe/<CODEX_THREAD_ID>.json`; the helper resolves this itself, so a normal save needs no separate environment lookup. For an explicit path, put options before the subcommand: `python3 <skill>/scripts/state.py --state PATH --owner SESSION_ID resume`; use its matching owner on creation and when another session ID is active in the environment. Use the same path for later calls. A `SessionStart` hook can inject compact/resume context for matching thread IDs. The supplied installer adds this hook without replacing existing hooks; the host still must trust the exact hook definition. Other hosts must explicitly run the same recovery read. Never claim that a file alone or a simulated event proves automatic host recovery.

## Clarify adaptively

Understand the intended change for the target user, full scope, environment, fixed decisions, and constraints. For existing projects inspect current behavior/data/policies before suggesting changes. If the user only knows the problem, propose product direction and capabilities with reasons and material alternatives. Do not reduce the assignment to an MVP.

Before presenting questions, check for omitted important areas answerable now: the actual failure point and success criteria, relevant actors' responsibilities/collaboration, and scope-changing exceptions/constraints. In the first response, broadly batch important independently answerable questions so the first user answer can advance clarification substantially; do not default to a small batch. Follow a user's request for smaller batches. Use relevance and answer dependencies, never a predetermined count. Use topic headings and numbered/subnumbered items as the default answer template. Elements that can clearly be answered together in one short sentence may share a number; give distinct short answer labels where needed. When different policies need separate explanations, give each its own number or subnumber; short labels do not turn long policy explanations into a short-sentence group. Apply this check to follow-up and restart questions too. A shared topic/state does not justify hiding complex policies in a paragraph. Apply this to enumerated targets, actions, stages, limits and detail inputs too. For partial answers to a grouped item, update only answered elements and leave the rest unresolved; never extend one answer to other elements. Do not re-split and re-ask a clear answer just to enforce numbering. Before batching, check whether a choice changes another question's need, actor or alternatives; defer such dependent details until that choice is answered. Batch independent important questions in followups too. After partial answers, update resolved items and ask only important unresolved ones. Reopen resolved items only for new evidence or relevant changes. Before turning a TBD into a question, compare current answers with the relevant requirements/acceptance and the relevant parts of any existing verification plan. Distinguish an undecided product choice, a decision resolved elsewhere, unperformed verification, and a decision deferred to a later stage. Respect source/confirmation status; a planned test or AI proposal is neither a user decision nor completed verification. Reuse resolved decisions and ask only remaining material choices needed now; clarify decision-changing conflicts or gaps without re-asking the settled scope. A TBD label or missing test result alone is not a reason to ask. Read relevant current material, not every document or question history. Grouping question wording does not merge independently verifiable requirement obligations or IDs under §5. Avoid fixed questionnaires, quotas, count-based completion and ordinary writing questions. Do not record question selection/checking processes.

Before sending a choice list, identify the decision each option changes. Alternatives for one decision and elements that can coexist need different wording. Keep coexisting elements individually answerable with short labels or multiple selection, and explicitly tell the user whether the displayed items can be combined. A recommended bundle must not silently decide another unanswered element. Check the actual wording, not only the topic; do not store this checking process.

Ask for a problem example when relevant to identify occurrence conditions and the handling/communication path; briefly explain that purpose. Work with what the user remembers without requiring an exact cause or responsible person. If no actual example is available or recalled, continue with ordinary workflow or anticipated/hypothetical situations. Distinguish actual facts from assumptions and hypothetical accounts; do not generalize one example into policy for every case. Keep only relevant current requirements, conditions and uncertainty, never a separate example transcript or investigation log.

Lead the first response with a short purpose and necessary recommendation, then the important questions. A concise explanation must not narrow the question coverage. Avoid a long speculative feature table or detailed design before answers. Explain recommendation reasons and material alternatives; use conditional recommendations when key facts are missing and allow “unknown/recommend for me.” Proposals become requirements only through user selection. Preserve important rejected/excluded scope without a rejection log; reopen it only when circumstances change.

For web projects read [web considerations](references/web.md); for a visual UI read [visual preferences](references/visual.md). These are conditional considerations and question sources, not automatic features, themes, or tool choices. Reuse existing answers; do not copy the annexes into the output or create permanent separate questionnaires.

Verify only missing facts/constraints that matter to requirements. For a new idea, do not guess-search for unprovided/unlocated files; retain preservation requirements and inspect material when supplied or its contents/location affect a current decision. Still inspect known existing-project behavior/data/policies. Preserve facts and source locations, not search history; stop with sufficient evidence and no known decision-changing conflict. Inaccessible material remains unresolved. Do not select implementation tools/methods here.

## Maintain one current requirements document

The current document is the `sections` map in the state file, not a transcript. Pick meaningful IDs for independent requirements; reserve `GOAL`, `SCOPE`, and `CONSTRAINTS` for shared current context, including important exclusions and cross-cutting confirmed preferences. Keep those facts once in shared context; link specialized sections to them instead of hiding them outside recovery or duplicating them. Section bodies are free-form Markdown, not a required handoff schema. Keep each fact once, with its source/status: user-confirmed, supplied requirement, externally evidenced, proposed, or unresolved. Store project facts and decisions rather than copies of skill operating rules or writing-process narration; retain project-specific scope and authorization boundaries. Initially store supplied facts, important exclusions and proposals/unknowns needed for current choices concisely; preserve their scope/conditions/exceptions/source/status. Detail the full scope as answers arrive instead of predicting a complete design before them. Never discard established meaning for brevity.

Apply the agreement's complete §5 stage criteria when their inputs are available. Connect each independent obligation's ID, source/goal, conditions, observable result, pass/fail, expected or actual evidence and status in the current body; absent evidence stays unverified. Preserve IDs, technical constraints and target/state/exception/failure differences. Keep required results, implementation choices and tests distinct. Detail screen flow and action/response/end/cancel behavior in text under §8. Do not force mature requirements from unanswered questions.

Before constructing a save patch, prepare and review the answer's changed text together with affected requirements, flows and acceptance under §5. Ordinary followups review that affected scope; final approval and requested whole-project reviews require the complete current scope under §9. Check accepted actors, targets, conditions and exceptions before serialization; do not broaden a named responsibility or leave it only in the conversational answer.

Run `python3 <skill>/scripts/state.py save` with the combined JSON patch on stdin. Accepted fields are `sections` (ID to current Markdown; null removes an obsolete section), `focus`/`pending` (existing section IDs), and `next` (next action). Send only changed fields; omit unchanged fields. This exact command needs no help lookup. Alternatively `python3 <skill>/scripts/state.py save --input PATH` reads your temporary patch; remove only your own transport after success, never user sources. Save meaningful decisions before dependent work; batch the answer and its applicable review in one save. In that same patch, update affected requirement bodies and remove or resolve answered TBDs together with `pending` and `next` as needed. Preserve decision IDs, conditions and exceptions. For partial answers retain only unanswered TBDs; keep a section pending while other unresolved decisions remain. Remove locations with no unresolved decisions from question waiting, even when verification is still unperformed; preserve planned/unverified evidence in the body. Base the next questions/actions on this updated state. Correct important defects found afterward; a write count is never a reason to leave them. No-op saves do not write. Never store whole questions/answers, recommendation/rejection processes, change reasons, before/after tables, or accumulating checkpoints. Progress pointers must not duplicate bodies. Pending sections may state influence/decision timing only when known.

For local changes update related requirements/flows/acceptance. For a shared policy change search the affected scope, not just explicit neighbors. No full dependency graph is required. `save` defaults to meaning-changing and clears old review/approval; `--editorial` is only for a host-confirmed meaning-preserving wording/layout change, never changed obligations, scope, exceptions, or evidence. The helper cannot determine semantic equivalence.

## Review, approve, and deliver

Review the complete current scope under §§5·9, including NASA quality, applicable acceptance and purpose-failure counterexamples, required state rules and important unknowns. Preserve §5's distinction between implementation correctness, user-purpose validation, formal-model limits and actual independent review. Judge criticism by source or counterexample, not votes/confidence/counts. Fix current sections without a review clone or reasons log; retain justified deferrals. A file or correct syntax is not quality proof.

After that host review, `save --reviewed` declares the current document ready for user confirmation (supply an empty patch on stdin if nothing changed). This flag serializes a host judgment and performs no semantic review. Present the complete requirements and remaining uncertainty to the user. Only after actual user confirmation use `approve --user-confirmed`; never infer it from silence, a benchmark prompt, or the flag's availability. Meaning changes after approval return to draft and require review/user confirmation again. Routine editorial changes can preserve approval.

Use `read --all` to render the final current document when needed. Include a short text invitation identifying useful follow-up areas; do not defer already-known important gaps into that invitation. After approval, pass this result to existing SynFrame normally, without a new strict intake contract or changes to SynFrame policy. Do not automatically build the product or install an external recovery skill. ProjectFrame coordination is a separate scope.

Validate coverage, independent answerability, recommendations, partial-answer reuse, resulting requirements and recovery meaning before costs. Assess the first batch's breadth and the continuing clarification: an item absent from the first response alone is not a defect; consider current answerability, prerequisites and actual followup resolution. Check for unnecessarily narrow first questions without grading by count or demanding mature specifications before answers. Compare reads/writes/context/tokens/time and unnecessary calls, including failures, with isolated inputs; separate useful-question time from progress notices and total time. Match comparison conditions or disclose differences and inseparable latency causes. Preserve agreement loading, recovery and final review. Do not collect operational transcripts. Distinguish structural checks, simulations, fresh-context behavior and real host compaction. Report unavailable measures as unavailable, never zero; evaluation cases are not presets.

Requirements engineering informs the stage criteria in the operating contract. Learning examples/history, fixed question caps and reason/change-report outputs from source prompts do not override user agreements. Do not re-load all source pages each turn or treat a study's limited result as general quality proof.
